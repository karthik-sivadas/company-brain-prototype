# Company Brain

One place where company knowledge lives, that can be **queried to get work done**, and that
anyone can extend by editing a folder.

Built by composing two tools instead of writing a platform:

| Layer | Tool | Why |
|---|---|---|
| **Extraction** | [`pm`](https://github.com/polymetrics-ai/cli) | 557 built-in connectors, incremental cursors, dedup, tombstones, run ledger, approval-gated writes |
| **Reasoning** | [`omp`](https://omp.sh) | agent loop, tool use, sessions, subagents, and skill discovery from a folder |
| **Query** | `duckdb` | reads pm's Parquet warehouse in place — no import step |
| **Knowledge** | `brain/` | skills, docs and captured answers as plain Markdown |

There is no bespoke agent runtime, no vector database and no application server.

## Prerequisites

| Tool | Version | Needed for |
|---|---|---|
| **Bun** | ≥ 1.1 | everything except the Slack bridge |
| **Node** | ≥ 22.7, < 26 | the Slack bridge only (`--experimental-transform-types` landed in 22.7 and was removed in 26) |
| **Go** + a C compiler | 1.25+ | the one-time pm build. CGO is required — the DuckDB driver will not link without it |
| **Docker** | daemon running | sandboxes and Slack. colima works |
| **duckdb** | any | host-side `ask` (the sandbox ships its own) |
| **omp** | latest | the agent runtime — **and it must be signed in to a model provider**, or every answer fails with "No models available" |

`bun run brain doctor` checks the first-party ones. It does **not** check that omp is signed
in, which is the most common silent failure.

## Quick start

```bash
bun install               # the README used to omit this

bun run brain doctor      # check prerequisites
bun run brain setup       # build pm, init the project, install skills, create connections
bun run brain sync        # extract into the warehouse
bun run brain ask "how many issues are synced, and the 3 newest?"
```

## How it fits together

```
sources ──▶ pm ──▶ data/pm/.polymetrics/warehouse/**/tables/*.parquet
                                    │
                    brain/skills/  ─┼─▶ omp ──▶ cited answer
                    brain/docs/     │
                    brain/memory/   │
                        (.omp/skills is a symlink to brain/skills)
```

**pm** runs offline on a schedule and owns everything hard about sync: what changed since last
time, deduplication by primary key, deletions, and a per-run ledger. **omp** answers questions by
reading `brain/skills/` and querying the warehouse with DuckDB. Retrieval is agentic — grep and
SQL over a modest corpus — rather than an embedding index, which is a later optimisation.

## The folder is the product

```
brain/
  skills/          how-to knowledge; omp discovers these automatically
    brain-search/  where the data is and how to query it (regenerated on each sync)
    brain-setup/   how to add a source, install skills, repair the brain
    pm-*/          generated by `pm skills generate` — one per connector
  docs/            SOPs and policies (Markdown)
  memory/facts/    answers captured from people
  agents/          personas
  .skills-catalog/ the other 549 connector skills, parked out of the agent's context
```

`pm skills generate` emits **564** skills. Their descriptions are what an agent loads at startup,
so only an allow-list (`activeSkills` in `brain.config.json`) stays in `brain/skills/`; the rest are
parked. That is what `bun run brain skills` does.

## Adding a data source

**Full guide: [docs/CONNECTORS.md](docs/CONNECTORS.md)** — how to pick a connector, read its
real primary key and cursor out of pm's manifest (guessing them creates a permanently broken
connection), supply credentials from `.env`, and verify the agent can see the result.

Once a connector is configured you rarely need to add streams by hand — ask the brain and it
extracts them itself.


Add an entry to `brain.config.json` and re-run setup:

```json
{
  "connector": "slack",
  "credential": "slack",
  "config": {},
  "fromEnv": { "access_token": "SLACK_BOT_TOKEN" },
  "streams": [
    { "name": "channel_messages", "primaryKey": "ts", "cursor": "ts",
      "table": "slack_messages", "syncMode": "full_refresh_overwrite" }
  ]
}
```

Secrets only ever appear as `fromEnv` mappings — pm reads the value from the environment, so no
token is written to config, logs or the warehouse.

Or just ask: `bun run brain ask "add Slack as a source"` — the `brain-setup` skill teaches omp the
procedure, and it will check the connector's real schema before answering.

- `pm` built from `polymetrics-ai/cli@main` — **557 executable connectors**

## Sandboxed execution

By default the agent runs on the host. It can also run inside a container, driven over OMP's
newline-delimited JSON RPC protocol:

```bash
bun run brain sandbox build
bun run brain sandbox ask "how many issues are synced?" needletail
bun run brain sandbox stop needletail
```

**One volume per workspace.** Each workspace name maps to exactly one Docker volume
(`brain-ws-<workspace>`) mounted at `/workspace` — the agent's sessions and scratch space, and the
only writable mount. It survives the container, so a workspace keeps its history.

| Mount | Mode | Why |
|---|---|---|
| `brain-ws-<workspace>` → `/workspace` | rw | the per-workspace volume: sessions, scratch |
| `brain/` → `/brain` | **ro** | the agent must not rewrite its own instructions |
| `warehouse/` → `/warehouse` | **ro** | it queries data; it cannot corrupt it |

The container runs non-root (uid 10001) with a read-only root filesystem, `--cap-drop=ALL`,
`--security-opt no-new-privileges`, memory and PID caps, and no Docker socket.

**Not yet done: authorization.** Model credentials are currently shared by mounting the host's
`~/.omp/agent`. Replacing that with a scoped, per-workspace token is the next piece of work.

## Slack

```bash
npm run slack:doctor           # tokens verified against Slack, scopes, channel membership
npm run slack:start            # Socket Mode bridge (no public URL needed)
./scripts/slack.sh threads     # known threads and their sandboxes

# The bridge runs on NODE, not Bun: @slack/socket-mode needs real undici's WebSocket and
# its pong diagnostics channel, neither of which Bun's undici shim provides. scripts/slack.sh
# picks a suitable Node (>=22.7, <26) even if an older one is first on PATH.
```

Ask in a channel (`@Company Brain …`) or DM. The answer returns in-thread with a ⏳ → ✅ reaction,
a tools/elapsed context line and 👍/👎 buttons.

**One sandbox and volume per Slack thread.** `brain-thread-<team>-<channel>-<ts>` /
`brain-ws-thread-…`. A thread registry (`data/slack/threads.json`, written atomically) survives
bridge restarts, so a message in an old thread is still recognised as a follow-up.

**Follow-ups keep context — verified.** Turn 1 stored a codeword, the container was destroyed, and
turn 2 in a brand-new container on the same volume recalled it. Continuation uses a per-thread
session directory plus `--continue`; a follow-up needs **no @mention** (plain `message` events are
accepted when the thread is already in the registry).

Turns for one thread are serialised — a session file cannot take concurrent writers — while
different threads run in parallel up to `BRAIN_MAX_CONCURRENT` (default 4). Idle containers are
reaped after `BRAIN_IDLE_REAP_MINUTES` (default 15); volumes, and therefore memory, persist.

Environment: `SLACK_BOT_TOKEN`, `SLACK_APP_TOKEN`, optional `SLACK_CHANNELS` (allow-list).

## Commands

| Command | Purpose |
|---|---|
| `bun run brain doctor` | check `omp`, `duckdb`, `go`, `git`, pm binary, project, skill link |
| `bun run brain build-pm` | clone and compile pm (needs Go; CGO is required by the DuckDB driver) |
| `bun run brain setup` | idempotent bootstrap |
| `bun run brain skills` | regenerate and transport skills |
| `bun run brain sync [connector]` | extract |
| `bun run brain tables` | list queryable Parquet tables |
| `bun run brain ask "…"` | ask a question on the host |
| `bun run brain sandbox build\|ask\|stop` | run the agent in a container, one volume per workspace |
| `npm run slack:doctor\|slack:start` | Slack bridge (Socket Mode), one sandbox per thread — runs on Node |

## Notes

- `pm` creates `.polymetrics/` in its working directory, so every invocation is pinned to `data/pm/`.
- A sync reporting `failed` with `page budget` in the error is expected when `max_pages` is set —
  the rows are committed. Use `"max_pages": "all"` for a complete pull.
- Public GitHub access needs both `auth_type=public` and `rate_limit_ip`.
- `omp` blocks on `readPipedInput` unless stdin is closed; the CLI handles this.
