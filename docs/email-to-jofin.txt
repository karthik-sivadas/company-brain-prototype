WHAT IT DOES

You ask a question in Slack. A container spins up for that thread, an agent queries
a local Parquet warehouse with DuckDB, and answers with a citation to the exact file
it read. If the data isn't there yet, it says so, extracts it, then answers. If you
ask it to change something in an external system, it doesn't — it posts an approval
card and waits for a person to press Approve.

Four things I verified by running them, not by reasoning about them:

  - Asked for release counts with nothing synced, it replied "Releases are not
    synced. I'm starting the configured GitHub extraction", created the connection,
    ran the sync, and answered: 4 releases, cited to the Parquet file.

  - A thread keeps its memory after its container is destroyed. I killed the
    container between turns and the conversation continued.

  - The full loop in Slack: I asked it to file an issue, it posted an approval card,
    I pressed Approve, and the issue appeared on GitHub. The agent proposed; it did
    not execute.

  - End to end against a real GitHub account: private repo created, issue created,
    closed, then deleted. Deleting additionally required typing "destructive" — the
    agent literally cannot approve its own writes, because pm withholds the approval
    token from its machine-readable output specifically so an agent can't authorise
    its own mutation.

HOW IT'S BUILT

This is the actual argument. I wrote no agent runtime, no vector database and no
application server. pm (Polymetrics CLI) owns extraction: cursors, deduplication,
tombstones, a run ledger, approval-gated writes. omp owns the agent loop. DuckDB
queries Parquet in place. Docker provides isolation. The repo is about 3,300 lines
of glue between them — built in one sitting, 16:13 to 22:31, 24 commits. Not because
I write fast, but because almost none of it was written.

ON CONNECTORS — AN HONEST ARCHITECTURAL CONSTRAINT

557 connectors are compiled into the binary, but the prototype runs with 17 enabled,
not 557. Every enabled skill's description ships in the agent's system prompt, so
enabling all of them would swamp its context before it read a single question — one
connector's skill file alone is 698 KB. So pm generates all 564 and the brain keeps
an allow-list of 17 active, with the rest parked one command away.

That's a deliberate trade, and it's the right shape: you enable the connectors a team
actually uses, not every connector that exists. Moving one from parked to active is a
config line.
